Featured project

TeleControl v4: a three-board control platform

Telecontrol
Sole developer and tester. Internal platform for the company's HVAC installations.

The successor to Telecontrol's previous controller: an HMI, a scriptable controller and an I/O board that supervises every output, all bare-metal on TM4C1294 and MSP430.

The platform is proprietary, so there is no code or repository here. What I can share is how it is built and why: the architecture and the engineering decisions behind it.

Why output safety lives on the MSP430, not in the scripts

Scripts change often and can fail; output safety cannot. The I/O board enforces minimum-on, maximum-on and cooldown limits per output, latches the emergency stop, and forces outputs safe on link loss or stale readings, even if the controller or HMI stops responding.

Why the control logic runs as Lua scripts

Application logic should change without rebuilding the firmware. Lua 5.5 runs on the Cortex-M4 in bounded scan cycles with static allocation only, and production scripts and timing maps are stored encrypted on SD.

Why every link carries a protocol version

Three boards are flashed separately, so a version mismatch is a real failure mode. The UART, SPI and RS-485 Modbus RTU links are versioned contracts, and both ends always change together.

Why testing starts off the board

Bench time is limited and failures on site are expensive. Host-side C unit tests with mocks and a PyQt HVAC plant simulator wired to the real controller catch logic errors first, and design decisions are recorded as architecture decision records.

About

I'm an embedded software engineer in Mexico City. At Telecontrol I design, write and test the firmware and tools behind the company's control platforms, from the safety supervisor to the touchscreen.

I care about firmware that stays predictable under failure: bounded loops, static memory, versioned protocols, and documentation good enough for the next engineer to change it safely.
